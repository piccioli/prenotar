## Codebase Patterns
- `Filament\Support\Colors\Color::hex('#rrggbb')` generates a full 50–950 shade
  palette from a single brand hex via `Color::generateShades()`: shade 500 is
  exactly the input color, every other shade (including 600, the default Filament
  "primary" reference shade) is algorithmically lightened/darkened from it — don't
  expect the exact input hex to reappear verbatim at 600 in the rendered CSS
  variables, that is expected Filament behaviour, not a bug.
- `->viteTheme('resources/css/filament/{panel}/theme.css')` resolves through
  Laravel's own `Illuminate\Foundation\Vite` invokable against the **default**
  `public/build/manifest.json` unless a custom `buildDirectory` (2nd arg) is
  passed — and passing one requires actually configuring `laravel-vite-plugin`
  to emit a separate manifest under that subdirectory. With a single shared
  `vite.config.js` input array (all 3 panel `theme.css` entries in one build),
  omit the 2nd arg entirely; all 3 panels resolve fine against the one manifest
  Vite already produces.
- Tailwind's `@config 'path.js';` directive must come **after** all `@import`
  statements in the same CSS file (postcss-import enforces "@import must precede
  all other statements"), otherwise `vite build` throws a warning per malformed
  file. Order per theme entry: `@import` (Filament base + our tokens) first,
  then `@config`, then any panel-specific `:root {}` overrides.
- Font self-hosting (no external CDN calls at runtime): use an npm package like
  `@fontsource/<font>` and `@import '@fontsource/<font>/latin.css';` from a CSS
  file processed by Vite — Vite's CSS pipeline resolves the node_modules import,
  rewrites the internal relative `url()`s and copies the woff/woff2 files into
  `public/build/assets/` with hashed names automatically. No manual asset
  copying needed. The per-subset files (`latin.css`, not `400.css` which bundles
  every unicode range including cyrillic/greek/vietnamese) keep the bundle lean
  when only Italian/Latin content is needed.
- `./vendor/bin/sail npm install` / `sail npm run build` work fine even though
  `node_modules` doesn't exist yet on host — Sail's `laravel.test` container has
  its own Node/npm, no need to install anything on the host machine.
- Design token source-of-truth files live in `tasks/design-reference/*/tokens/*.css`
  but per that folder's own README they are "materiale di progettazione ...
  non renderizzabile standalone ... non va servito dall'app": don't `@import`
  them directly into a compiled bundle. Copy the values 1:1 into the app's own
  `resources/css/...` tree (with a comment noting the source of truth), so the
  design-reference folder is read-only reference material, never shipped.
- Extending Filament panel layout without forking the package: use
  `Panel::renderHook(\Filament\View\PanelsRenderHook::X, fn (): string => view(...)->render())`
  in the `*PanelProvider::panel()` chain (list of slots in
  `vendor/filament/filament/src/View/PanelsRenderHook.php`, e.g. `TOPBAR_START`,
  `TOPBAR_END`, `BODY_END`). These closures run on every request (not cached),
  so route-based "is this nav item active" logic can live inline via
  `request()->routeIs('filament.<panel>.pages.dashboard')` /
  `request()->routeIs([...])` (array = OR match) with no extra state needed.
  `renderHook()` also accepts a `$scopes` 3rd arg (page/Livewire component
  class name(s)) to target a hook at one specific page only — useful for
  page-specific additions (e.g. a FAB) without touching the shared panel-wide
  hooks.
- With Filament's default **sidebar** navigation (not top navigation), the
  brand logo/name is rendered inside the sidebar header, NOT in the topbar —
  on mobile, with the sidebar collapsed off-canvas by default, the topbar
  shows only the hamburger button and nothing else unless you inject
  something via `TOPBAR_START`/`TOPBAR_END`.
- Resource route names follow `filament.<panel>.resources.<slug>.<index|create|view|edit>`
  where `<slug>` is the auto-pluralized model name (e.g. `Prenotazione` →
  `prenotaziones`, `Torre` → `torres`, not Italian-correct plurals) and page
  routes follow `filament.<panel>.pages.<page-slug>` (dashboard included, e.g.
  `filament.sezione.pages.dashboard`) — confirmed via
  `sail artisan route:list`, don't guess these from the resource/page class name.

  `sail artisan tinker --execute="..."` to build a `Request`, call
  `app()->handle($request)` as an authenticated seeded user, and grep the

- Per-row dynamic (non-palette) colors on a Filament `TextColumn`/`TextEntry`
  badge: `->color()` accepts a closure returning a `Filament\Support\Colors\Color::hex($hex)`
  array (the 50–950 shade map), evaluated per-row via Filament's own closure
  injection (typed `$record` param resolved automatically, no manual binding
  needed) — this renders via inline CSS custom properties
  (`vendor/filament/support/src/helpers.php` `get_color_css_variables()`), NOT
  via the registered-palette-name system, so no `FilamentColor::register()` or
  Tailwind safelisting is needed for arbitrary hex values coming from a DB
  column. A **raw hex string** passed directly to `->color()` does NOT work
  (it's treated as a palette *name* lookup, e.g. `var(--#1D574B-500)`, which
  doesn't exist) — always wrap with `Color::hex()` first.
- Larastan gotcha: `$record->torre?->colore_hex ?? 'fallback'` (nullsafe on a
  `BelongsTo` magic relation property, combined with `??`) trips the
  `nullsafe.neverNull` rule even when the FK column genuinely is nullable in
  the migration (`foreignId('torre_id')->nullable()`) — Larastan's relation
  type inference for magic properties doesn't factor in DB-level nullability
  here, so it wrongly claims the relation is never null. Don't blindly follow
  its "use -> instead" suggestion (that produces a real null-pointer risk at
  runtime, since the relation genuinely can be null). Instead extract a small
  static helper with an explicitly nullable typed parameter, e.g.
  `Model::helperMethod(?self $model): string { return $model === null ? ... : ...; }`,
  and call it as `Helper::helperMethod($record->relation)` (plain `->`, no
  nullsafe operator at the call site) — this satisfies Larastan AND centralizes
  the "what's the fallback for a missing related record" logic in one place
  instead of duplicating a ternary at every call site.
- The `nullsafe.neverNull` false positive above isn't limited to magic
  relation properties: it also fires on a plain local `?Model` variable
  obtained from `Model::find($value)` when `$value` has static type `mixed`
  (e.g. it came from a Filament closure param like `Get $get`, whose
  `__invoke()` returns `mixed`) — Larastan loses the nullability of `find()`'s
  return type end-to-end in that case too. Same fix: a static helper with an
  explicitly nullable typed parameter, plain `->` inside.
- Deep-linking to a specific step of a Filament `Wizard` from arbitrary content
  nested inside it (e.g. a "Modifica"/"Edit" link on a review/summary step):
  `x-on:click="step = @js($stepId)"` works anywhere in the DOM as long as it's
  nested inside the same root `x-data` as the Wizard (i.e. inside any of its
  Steps' own content) — `step` is the Alpine variable `wizard.blade.php`
  already tracks. `$stepId` must be the auto-generated slug-id Filament gives
  each `Wizard\Step` (`Str::slug(Str::transliterate($label, strict: true))` of
  its label) — verify it in `tinker` first, never guess it from the label text.
- Custom "card-style" presentation for a Filament form field (e.g. selectable
  cards instead of a plain `<select>`, or a stateful colored info box instead
  of a plain checkbox) without forking the package or writing a Livewire
  component: any `Forms\Components\*` Field (`Radio`, `Checkbox`, etc.) can
  call `->view('your.custom.view')` (inherited from
  `Filament\Support\Components\ViewComponent`) to swap only its Blade template
  while keeping 100% of the original state binding/validation/`live()`/
  `afterStateUpdated()` logic untouched — copy the relevant bits from the
  stock view (e.g. `vendor/filament/forms/resources/views/components/radio.blade.php`)
  for the input itself (`<x-filament::input.radio>` / `<x-filament::input.checkbox>`,
  `$applyStateBindingModifiers('wire:model')`, `$getExtraInputAttributeBag()`,
  `$errors->has($statePath)`) and freely restyle everything around it. Every
  public method of the component (`$getOptions()`, `$getState()`, `$isDisabled()`,
  `$isOptionDisabled()`, etc.) is auto-extracted into the Blade scope, so no
  extra wiring is needed. Use `->viewData(fn (Get $get) => [...])` (also
  inherited from `ViewComponent`) to inject extra data a plain option/label
  can't carry (e.g. a related model instance) — the closure is evaluated via
  Filament's own closure-injection (`Get $get`, `$record`, etc. resolved by
  parameter name/type), exactly like `->visible()` or `->content()` closures.
- A `Radio`/`Select` "no selection" placeholder can be turned into a real,
  clickable option (e.g. an explicit "Nessuna preferenza" card) by adding an
  option with key `''` (empty string) instead of relying on a `->placeholder()`
  (which Radio doesn't support anyway). Existing `$get('field') ? ... : null`
  ternaries elsewhere in the form (rules, etc.) keep working unchanged since
  `''` is falsy in PHP, exactly like `null` — the only place that needs an
  explicit adjustment is dehydration before save: add
  `->dehydrateStateUsing(fn ($state) => filled($state) ? (int) $state : null)`
  so the empty-string sentinel never reaches an integer/nullable FK DB column.
- Filament's `Wizard` component footer (Annulla/Continua/Salva buttons) is
  rendered entirely by `vendor/filament/forms/resources/views/components/wizard.blade.php`
  with no slot for extra per-step content beside the buttons — short of
  forking that view via `Wizard::make(...)->view(...)`, an explanatory message
  about why "Continua" is disabled has to live inside the step's own content
  (e.g. inside the same colored info box that blocks the button), not literally
  beside the button as some mockups draw it. **Update (US-007): forking IS
  viable and not that costly** — `Wizard` extends `Component` extends
  `ViewComponent` exactly like `Radio`/`Checkbox`, so `->view('custom.blade')`
  works on it too. Copy vendor's `wizard.blade.php` verbatim (same `x-data`/
  `x-init`/Alpine functions), then only add new markup + toggle `hidden md:*`
  classes on the parts you want to replace per breakpoint — every Alpine
  function (`getStepIndex`, `isFirstStep`, `isLastStep`, `previousStep`, the
  `$wire.dispatchFormEvent('wizard::nextStep', ...)` call) keeps working
  because the new markup lives inside the same root `x-data` div. A per-step
  "why is Continua disabled" hint string CAN reach that forked view without
  duplicating the disabling condition: extract the condition to a local
  closure variable once in the page's `form()` method, pass it to both
  `->nextAction(fn ($action) => $action->disabled($condition))` and
  `->viewData(fn (Get $get) => ['hint' => $condition($get) ? '...' : null])`
  (same source, evaluated twice, not two implementations).
- Rendering the same Filament `Action` object (e.g. a Wizard's `$nextAction`)
  twice in one Blade view (once for a desktop-only footer, once for a
  mobile-only fixed footer, toggled via `hidden md:flex` / `md:hidden`) is safe
  functionally (both copies are purely presentational registrations of
  `x-on:click`/`wire:loading.class` on their own wrapping `<span>`, no
  `document.getElementById` dependency) but produces two DOM nodes sharing the
  same `id` — invalid HTML. Prefer building the second (mobile) instance as a
  plain `<x-filament::button>` reading `$action->getLabel()`/`->getColor()`/
  `->isDisabled()` (not re-rendering `{{ $action }}` itself) so there is one
  real Action element and one lightweight styled clone, and pass
  `?? 'primary'` when forwarding `->getColor()` into `<x-filament::button
  :color="...">` — that prop's Blade `@props` default only applies when the
  key is *absent*, not when explicitly `null` (which is what an unstyled
  Wizard next-action's `getColor()` returns), so an unguarded pass-through
  silently loses the primary styling.
- To hide one globally-registered `renderHook()` element (e.g. the shared
  mobile bottom tab bar from US-002) on a single page without touching the
  `*PanelProvider`'s render hook itself: give that page's own Blade template a
  distinguishing class (Filament's stock `CreateRecord` page view already
  emits `fi-resource-create-record-page` + `fi-resource-{slug}`) and add a
  scoped CSS rule (`.fi-resource-<slug>.fi-resource-create-record-page
  .fi-mobile-bottom-nav { display: none }`) in the shared mobile-shell
  stylesheet — no PHP/render-hook changes needed, and it stays obviously
  scoped to that one page's classes instead of a global toggle.
- Correction to the US-006 note about `Livewire::test()` outside a real HTTP
  cycle: it DOES resolve the current Filament panel correctly, as long as
  `Filament::setCurrentPanel(Filament::getPanel('<id>'))` is called explicitly
  before `Livewire::test(...)` in the tinker/script context (a real HTTP
  request resolves this automatically via panel routing middleware; tinker
  doesn't go through that middleware, so it must be done by hand). With that
  one extra line, `Livewire::test(Page::class)->set('data.field', $value)->html()`
  works fine in `sail artisan tinker` for verifying **reactive** `->live()`
  state (colors/messages that only appear after a field changes), which plain
  `app()->handle($request)` (US-001 through US-006's usual no-browser
  verification technique) cannot exercise since it only ever renders the
  initial GET state.
- A generic "radio card" Blade view (bordered clickable card, title + optional
  subtitle, no torre-specific color dot/address) lives at
  `resources/views/filament/sezione/forms/components/radio-option-cards.blade.php`:
  unlike `torre-radio-cards.blade.php` (US-006, hardcoded `Torre::find()`
  lookup), it reads only `$hasDescription($value)`/`$getDescription($value)`
  (native `Radio`/`HasDescriptions` methods, set via `->descriptions([...])`)
  — reuse this for any future simple "select one of N options as a card"
  field instead of writing a new view per field.
- `Forms\Components\ToggleButtons::make(...)->grouped()->inline()` is the
  closest core-Filament component to a mockup "segmented pill toggle" (2+
  mutually exclusive states rendered as a `fi-btn-group`) — prefer it over
  `Radio->inline()` when a mockup shows a pill instead of radio dots. It
  ALWAYS needs an explicit `->colors([...])` per option value (never leave it
  unset/`null`): the grouped view passes `:color="$getColor($value)"`
  straight into `<x-filament::button>`, and an explicit `null` there silently
  loses the "primary" default (same `@props` gotcha already noted above for
  Wizard actions) instead of falling back to the panel's primary color.
- When several elements in the same `Step`/`Section` schema need to share one
  visibility/required condition (e.g. "mezzo privato" toggles both a whole
  `Section` on and an unrelated hint `Placeholder` off), pass a **closure** to
  `->schema(function (): array { ... return [...]; })` instead of a static
  array — Filament's `schema()` accepts either, and the closure form lets you
  declare the shared condition variable once in scope and reuse it across
  multiple `->visible()`/`->required()` calls without duplicating the ternary.
- The `->view()` swap technique (copy vendor's Blade template, wrap with custom
  markup, keep 100% of the original Alpine/Livewire logic) also works for
  `FileUpload`/`SpatieMediaLibraryFileUpload`, not just simple fields like
  `Radio`/`Checkbox`: copy `vendor/filament/forms/resources/views/components/file-upload.blade.php`
  verbatim (the `x-data="fileUploadFormComponent({...})"` block, the hidden
  `<input type="file">`, the error text) and add your own status markup around
  it. The component's own public getters (`$getRecord()`, `$getCollection()`
  on `SpatieMediaLibraryFileUpload`) are auto-extracted into the Blade scope
  like any other field, so per-record/per-collection dynamic state (e.g. "is a
  file already uploaded, and what's its name/date") can be computed directly
  in the view with no extra `->viewData()` wiring. If none of the fields using
  this view have `->imageEditor()` enabled, the vendor's image-editor modal
  block can be dropped entirely (it would never render) instead of copied —
  verify first, don't drop it blindly. Genuine limitation: FilePond (the JS
  library actually rendering the dropzone/thumbnails/progress bar) can't be
  restyled into a single compact "Carica"/"Sostituisci" button purely via this
  technique — that would require touching FilePond's own JS options/CSS, out
  of scope for a Blade-only "solo presentazione" restyle.
- To embed a real, fully-functional action button **inside** a form schema
  (not a header action, not a table row action — e.g. to match a mockup where
  an action button lives in the page body instead of the header):
  `Forms\Components\Actions::make([Forms\Components\Actions\Action::make('name')
  ...->action(fn (?Model $record, Forms\Components\Actions\Action $action) => ...)])`.
  This is a **different** `Action` class from `Filament\Actions\Action` (used
  by header/table actions) but supports the identical fluent API (`->color()`,
  `->icon()`, `->disabled()`, `->requiresConfirmation()`, `->modalHeading()`),
  and closures resolve `?Model $record`/the action itself by parameter
  name/type exactly like any other Filament closure — `$action->redirect($url)`
  works directly, no need to inject `$livewire`. To test such an action:
  the auto-generated component key (verify via `$form->getComponents()` walk
  in tinker, don't guess) is `"{$form->getStatePath()}.{$actionName}Action"`,
  and Filament's Livewire testing macros want the key **without** the
  statePath prefix: `Livewire::test(Page::class, ['record' => $id])
  ->assertFormComponentActionDisabled('nameAction', 'name')` /
  `->callFormComponentAction('nameAction', 'name')`. Also note `->disabled()`
  on any Action (header, table, or form-embedded) is presentation-only — it
  does not stop the `->action()` closure from executing if called directly
  bypassing the UI, so any real guard against invalid state transitions must
  still live at the domain/service layer, not rely on the disabled flag.

- **Learnings for future iterations:**
  - Vedi le 2 nuove voci in Codebase Patterns sotto (fork leggero di `FileUpload`/`SpatieMediaLibraryFileUpload` via `->view()` senza toccare la logica FilePond, e il pattern per testare un'`Actions::make()` form-embedded via `assertFormComponentActionDisabled`/`callFormComponentAction`) — rilevanti per qualunque story futura che debba mostrare stato dinamico su un campo file o spostare un'azione da header a corpo pagina (candidate: US-020/US-021 "Dettaglio prenotazione GR" con azioni condizionate allo stato, se dovessero richiedere un pattern simile).
  - `Forms\Components\Actions` (namespace `Filament\Forms\Components\Actions`) e `Forms\Components\Actions\Action` (namespace annidato `Filament\Forms\Components\Actions\Action`, diverso da `Filament\Actions\Action` usato negli header/table actions) sono la via per incorporare pulsanti-azione **dentro** lo schema di un form Filament (non nell'header né in una colonna tabella): supportano la stessa API fluente (`->color()`, `->icon()`, `->disabled()`, `->requiresConfirmation()`, `->modalHeading()`, `->action(closure)`), la closure risolve `?Model $record`/il proprio `Action $action` (via nome parametro) esattamente come le action "normali", e `$action->redirect($url)` funziona senza bisogno di iniettare `$livewire`.
