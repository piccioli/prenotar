## Codebase Patterns
- `database/factories/PrenotazioneFactory.php` (and Eloquent factories in general) run under `Model::unguarded()`, so the `definition()` array bypasses `$fillable` entirely and is inserted raw. Dropping/renaming a DB column requires updating every factory that sets it directly, even though normal mass-assignment (`Model::create()`) would silently ignore an unfillable key with no error.
- When removing a DB column that a Filament Infolist/Form still binds via `TextEntry::make('col')->visible(fn (Model $r) => $r->col === Enum::X)`, Larastan (property.notFound) catches property-access closures immediately even though `TextEntry::make('col')` by itself (string key, no property access) does not - property-access closures referencing dropped columns are the first thing to break statically.
- Full QA loop for this project: `./vendor/bin/sail composer qa` (Pint + Larastan level 6 + Pest). Pest here uses a real MariaDB `testing` DB via `RefreshDatabase`, so schema changes are exercised for real, not mocked.

- **Learnings for future iterations:**
  - `PrenotazioneResource.php` ha due schema form paralleli e duplicati: `wizardSteps()` (usato solo da `CreatePrenotazione`, mai con un record esistente) e `form()` (usato da `EditPrenotazione`, sempre con un record esistente). Ogni volta che si tocca una sezione presente in entrambi bisogna aggiornarli in coppia — sono rimasti sincronizzati "a mano" finora, nessuna astrazione condivisa.
  - Per un campo checkbox che deve tradursi in un timestamp DB (pattern "conferma -> `*_at`"): checkbox virtuale con `dehydrated(false)` + `rules(['accepted'])` + `afterStateUpdated(fn ($state, Set $set) => $set('campo_at', $state ? now() : null))`, accoppiata a un `Hidden::make('campo_at')` che e' il campo realmente dehydrated/salvato. Su `form()` (contesto edit, record esistente) serve in aggiunta `afterStateHydrated` per pre-spuntare la checkbox leggendo il valore attuale del record; sul wizard di create non serve mai (nessun record al mount).
  - Per validazioni cross-field tra due `DatePicker` nello stesso multi-step form (anche across step diversi), il pattern consolidato e' una classe `ValidationRule` dedicata (vedi `NoOverlapTorre`, e ora `DataRitiroEntroInizioPrenotazione`) istanziata dentro `->rules(fn (Forms\Get $get): array => [...])`, leggendo l'altro campo con `$get('altro_campo')` — funziona anche se l'altro campo e' in uno step precedente del wizard, gia' visto altrove nel file (es. `minDate` di `data_inizio_evento` legge `data_inizio_prenotazione`).
