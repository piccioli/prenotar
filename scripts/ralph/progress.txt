## Codebase Patterns
- Filament `Pages\Auth\Login::authenticate()` checks `$user->canAccessPanel(Filament::getCurrentPanel())` for the CURRENT panel — a shared/neutral panel with no real resources needs its own Login subclass overriding `authenticate()` to check `canAccessPanel()` against the real panels instead (`admin`/`gr`/`sezione`), otherwise every login on that panel is rejected and immediately logged out.
- `Panel::getUrl()` builds its result via a `NavigationManager` that reads `Filament::getCurrentPanel()` internally (global state), NOT the panel instance it's called on — calling `Filament::getPanel('admin')->getUrl()` from a *different* panel's request context does not reliably resolve `/admin`. Use `url($panel->getPath())` instead when you need another panel's base URL from outside its own context.
- A panel can have `->path('')` (empty string) to serve routes at the domain root (e.g. a shared `/login` panel) without colliding with the other panels' non-empty path prefixes.
- Every new Filament `viteTheme()` entry point must be added to `input` in `vite.config.js` AND rebuilt with `sail npm run build` before the page is requested — otherwise Filament throws a Vite-manifest-not-found error. `public/build/manifest.json` is gitignored, so this rebuild has to happen in every environment (dev machine, CI, deploy) that serves the new panel, not just once.
