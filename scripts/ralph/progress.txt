## Codebase Patterns
- Per trasformare una pagina `ListRecords` Filament da tabella (desktop) a
  card (mobile) senza duplicare query/tab/paginazione: override `protected
  static string $view` sulla sottoclasse `ListRecords` con un template Blade
  copiato da `vendor/filament/filament/resources/views/resources/pages/list-records.blade.php`,
  avvolgere `{{ $this->table }}` in un `<div class="hidden md:block">`, e sotto
  aggiungere un `<div class="... md:hidden">` che itera
  `$this->getTableRecords()` (metodo pubblico di
  `Filament\Tables\Concerns\HasRecords`, disponibile su ogni pagina/Livewire
  component che usa `InteractsWithTable`): ritorna la STESSA collection
  Eloquent paginata/filtrata/ordinata già usata dalla tabella (cache interna
  per-request, nessuna query duplicata), quindi tab attive (`getTabs()`),
  ricerca, sort e paginazione restano automaticamente in sync tra le due
  presentazioni senza riscrivere nulla di quella logica. Per l'empty state e
  la paginazione lato mobile, riusare gli stessi metodi pubblici già esposti
  dall'oggetto `Table` (`$this->getTable()->getEmptyStateHeading()/
  ->getEmptyStateDescription()/->getEmptyStateIcon()`,
  `->getPaginationPageOptions()`, `->hasExtremePaginationLinks()`) invece di
  duplicare le stringhe/opzioni già configurate in `table()`, e il componente
  Blade `<x-filament::pagination :paginator="$records" ... />` funziona identico
  fuori dal contesto `filament-tables::index` (nessuna dipendenza nascosta dal
  partial originale). Nota: il `<table>` HTML resta comunque nel DOM sotto il
  breakpoint mobile (solo nascosto via CSS `hidden`/`display:none`), coerente
  con la tecnica di "doppio rendering, toggle via classi responsive" già
  documentata sopra per il footer del Wizard — non è un `<table>` rimosso dal
  markup, se un AC richiede letteralmente zero nodi `<table>` nel DOM va
  verificato che questa interpretazione sia accettabile.
- Filament valorizza `->color()` di un `Tab` di default su `primary`: per
  restylare le tab standard (`<x-filament::tabs>`/`fi-tabs`/`fi-tabs-item`/
  `fi-active`) come un selettore a pillole segmentate (mockup mobile "Attive/
  Archivio"), le classi CSS sono stabili e restano targettabili via selettore
  scoped (`.fi-resource-<slug>.fi-resource-list-records-page .fi-tabs...`)
  senza toccare `getTabs()`/Blade — ma il badge del conteggio (`->badge(N)`)
  resta un `<x-filament::badge>` separato dentro il tab item, non testo inline
  tipo "Attive (4)": per un match pixel-perfect di quel formato va sostituita
  la label del tab con una stringa già comprensiva del conteggio invece di
  usare `->badge()`, altrimenti resta un chip adiacente (approccio scelto qui
  per non duplicare la logica di conteggio già in `getTabs()`).
- `Filament\Support\Colors\Color::hex('#rrggbb')` generates a full 50–950 shade
  palette from a single brand hex via `Color::generateShades()`: shade 500 is
  exactly the input color, every other shade (including 600, the default Filament
  "primary" reference shade) is algorithmically lightened/darkened from it — don't
  expect the exact input hex to reappear verbatim at 600 in the rendered CSS
  variables, that is expected Filament behaviour, not a bug.
- `->viteTheme('resources/css/filament/{panel}/theme.css')` resolves through
  Laravel's own `Illuminate\Foundation\Vite` invokable against the **default**
  `public/build/manifest.json` unless a custom `buildDirectory` (2nd arg) is
  passed — and passing one requires actually configuring `laravel-vite-plugin`
  to emit a separate manifest under that subdirectory. With a single shared
  `vite.config.js` input array (all 3 panel `theme.css` entries in one build),
  omit the 2nd arg entirely; all 3 panels resolve fine against the one manifest
  Vite already produces.
- Tailwind's `@config 'path.js';` directive must come **after** all `@import`
  statements in the same CSS file (postcss-import enforces "@import must precede
  all other statements"), otherwise `vite build` throws a warning per malformed
  file. Order per theme entry: `@import` (Filament base + our tokens) first,
  then `@config`, then any panel-specific `:root {}` overrides.
- Font self-hosting (no external CDN calls at runtime): use an npm package like
  `@fontsource/<font>` and `@import '@fontsource/<font>/latin.css';` from a CSS
  file processed by Vite — Vite's CSS pipeline resolves the node_modules import,
  rewrites the internal relative `url()`s and copies the woff/woff2 files into
  `public/build/assets/` with hashed names automatically. No manual asset
  copying needed. The per-subset files (`latin.css`, not `400.css` which bundles
  every unicode range including cyrillic/greek/vietnamese) keep the bundle lean
  when only Italian/Latin content is needed.
- `./vendor/bin/sail npm install` / `sail npm run build` work fine even though
  `node_modules` doesn't exist yet on host — Sail's `laravel.test` container has

- Per-row dynamic (non-palette) colors on a Filament `TextColumn`/`TextEntry`
  badge: `->color()` accepts a closure returning a `Filament\Support\Colors\Color::hex($hex)`
  array (the 50–950 shade map), evaluated per-row via Filament's own closure
  injection (typed `$record` param resolved automatically, no manual binding
  needed) — this renders via inline CSS custom properties
  (`vendor/filament/support/src/helpers.php` `get_color_css_variables()`), NOT
  via the registered-palette-name system, so no `FilamentColor::register()` or
  Tailwind safelisting is needed for arbitrary hex values coming from a DB
  column. A **raw hex string** passed directly to `->color()` does NOT work
  (it's treated as a palette *name* lookup, e.g. `var(--#1D574B-500)`, which
  doesn't exist) — always wrap with `Color::hex()` first.
- Larastan gotcha: `$record->torre?->colore_hex ?? 'fallback'` (nullsafe on a
  `BelongsTo` magic relation property, combined with `??`) trips the
  `nullsafe.neverNull` rule even when the FK column genuinely is nullable in
  the migration (`foreignId('torre_id')->nullable()`) — Larastan's relation
  type inference for magic properties doesn't factor in DB-level nullability
  here, so it wrongly claims the relation is never null. Don't blindly follow
  its "use -> instead" suggestion (that produces a real null-pointer risk at
  runtime, since the relation genuinely can be null). Instead extract a small
  static helper with an explicitly nullable typed parameter, e.g.
  `Model::helperMethod(?self $model): string { return $model === null ? ... : ...; }`,
  and call it as `Helper::helperMethod($record->relation)` (plain `->`, no
  nullsafe operator at the call site) — this satisfies Larastan AND centralizes
  the "what's the fallback for a missing related record" logic in one place
  instead of duplicating a ternary at every call site.
- The `nullsafe.neverNull` false positive above isn't limited to magic
  relation properties: it also fires on a plain local `?Model` variable
  obtained from `Model::find($value)` when `$value` has static type `mixed`
  (e.g. it came from a Filament closure param like `Get $get`, whose
  `__invoke()` returns `mixed`) — Larastan loses the nullability of `find()`'s
  return type end-to-end in that case too. Same fix: a static helper with an
  explicitly nullable typed parameter, plain `->` inside.

- To embed a real, fully-functional action button **inside** a form schema
  (not a header action, not a table row action — e.g. to match a mockup where
  an action button lives in the page body instead of the header):
  `Forms\Components\Actions::make([Forms\Components\Actions\Action::make('name')
  ...->action(fn (?Model $record, Forms\Components\Actions\Action $action) => ...)])`.
  This is a **different** `Action` class from `Filament\Actions\Action` (used
  by header/table actions) but supports the identical fluent API (`->color()`,
  `->icon()`, `->disabled()`, `->requiresConfirmation()`, `->modalHeading()`),
  and closures resolve `?Model $record`/the action itself by parameter
  name/type exactly like any other Filament closure — `$action->redirect($url)`
  works directly, no need to inject `$livewire`. To test such an action:
  the auto-generated component key (verify via `$form->getComponents()` walk
  in tinker, don't guess) is `"{$form->getStatePath()}.{$actionName}Action"`,
  and Filament's Livewire testing macros want the key **without** the
  statePath prefix: `Livewire::test(Page::class, ['record' => $id])

  `->callFormComponentAction('nameAction', 'name')`. Also note `->disabled()`
  on any Action (header, table, or form-embedded) is presentation-only — it
  does not stop the `->action()` closure from executing if called directly
  bypassing the UI, so any real guard against invalid state transitions must
  still live at the domain/service layer, not rely on the disabled flag.
- `Filament\Resources\Resource::getUrl($name, $params)` without an explicit
  `panel:` argument resolves the route base name against
  `Filament::getCurrentPanel()` (the panel active for the **current request**),
  NOT the panel the Resource class is registered to. This matters when a
  Livewire widget/component is shared across panels (e.g.
  `CalendarioPrenotazioniWidget` lives under `App\Filament\Sezione\Widgets` but

  when rendered inside `/gr`, which doesn't exist and throws. Always pass the

  code that isn't 100% guaranteed to run only within its own panel's request
  context.

  calls `$component->getKey()` even on the successful branch (e.g.
  `assertInfolistActionDoesNotExist`'s `Assert::assertNull($action, message:
  "...{$component->getKey()}...")`), so a `null` `$component` crashes with
  "Call to a member function getKey() on null" regardless of pass/fail. When
  an entire action group is gated behind an outer `->visible()` (not just
  the individual actions), test that case with a plain
  `->assertDontSee($action->getLabel())` on the rendered HTML instead of any
  `assertInfolistAction*` helper.
- `Filament\Infolists\Components\Section` (and `TextEntry`, `Tabs\Tab`, etc.)
  support `->icon()`/`->iconColor()` natively (via the shared `HasIcon`/
  `HasIconColor` traits already used by Actions) — no `->view()` fork needed
  to add a heading icon to an Infolist card, unlike some of the earlier
  form-field restyles in this epic that did require forking a Blade view.
  `Filament\Infolists\Components\Grid::make(['default' => 1, 'lg' => N])` +
  `Group::make([...])->columnSpan(['lg' => N])` gives the same responsive
  multi-column layout capability Forms already has, reusable for any
  Infolist page that needs a "main content + sidebar" 2-column mockup layout.
- A Blade view living under `resources/views/filament/components/*.blade.php`
  (the convention already used by `mobile-fab.blade.php`/`mobile-bottom-nav.blade.php`,
  registered under the plain Laravel `filament.components.*` view path, NOT a
  package-registered component namespace like Filament's own `filament::`) can
  only be invoked via `view('filament.components.x', [...])->render()` or
  `@include('filament.components.x', [...])` — **not** via the `<x-...>` tag
  syntax. `<x-filament.components.x />` resolves through Blade's default
  anonymous-component resolution, which always prefixes with `components.`
  (i.e. it looks for view `components.filament.components.x`, which doesn't
  exist) and throws `Unable to locate a class or view for component [...]`
  at render time — not a Larastan/Pint-time error, so it only surfaces when a
  Pest test (or a real request) actually renders that page. `@props([...])`
  inside such a view still works fine when invoked via `@include`/`view()->render()`
  (confirmed: `mobile-fab.blade.php` already does this), so no need to strip
  `@props` — just don't reach for the `<x-...>` tag for these.
- To add mobile-only chrome (a sticky back-arrow bar, a banner, etc.) to a
  SINGLE Filament page rather than the whole panel (contrast with the shared
  shell of US-002, which is unscoped): `renderHook(HOOK, closure, scopes:
  [PageClass::class])`. `PanelsRenderHook::PAGE_START` fires before the
  standard `getTitle()/getSubheading()` header (outside the `<section>` that
  wraps it, per `vendor/filament/filament/resources/views/components/page/index.blade.php`),
  so it's the right slot for anything meant to appear above that header without
  touching it. The scope to pass is the Page's own class (`getRenderHookScopes()`
  in `Filament\Pages\BasePage` always includes `static::class` of the current
  Livewire page component), not a route name or resource slug.
- When the SAME Filament Action (Infolist or Form) needs to be clickable from
  two different DOM locations simultaneously (e.g. a desktop card AND a fixed
  mobile action bar, both server-rendered and toggled by responsive CSS —
  contrast with the "one element, responsive CSS" pattern used elsewhere in
  this repo), you cannot reuse the same PHP Action instance twice in the
  schema tree. Extract its definition (form + `->action()` closure) into a
  private method taking an optional `$name` parameter, and call it twice with
  different names (e.g. `approva` / `approva_mobile`) to avoid Livewire action
  name collisions between the two mounted instances — confirmed via
  `Livewire::test()->callInfolistAction()` that triggering either instance
  runs the identical underlying logic, so behavior stays in sync automatically.
- A top-level `Infolists\Components\Group` placed as a sibling of a
  `Tabs::make()` in the same `$infolist->schema([...])` array stays visible
  regardless of which tab is active (unlike anything nested inside a
  `Tabs\Tab::make()->schema([...])`, which only renders for its own tab) —
  the right place for any "persistent across tabs" element such as a fixed
  action bar, no need to duplicate it into every `Tab`.
- Known, pre-existing, accepted overlap: any `fixed inset-x-0 bottom-0
  md:hidden` bar added by a page/wizard shares screen space with the panel's
  global bottom tab nav (`mobile-bottom-nav.blade.php`, unscoped `BODY_END`
  renderHook, present on every page). A higher `z-index` (e.g. `z-40` vs the
  nav's `z-30`) combined with an opaque background and a taller bar is enough
  to visually cover the nav completely — no need to hide the global nav or
  scope its renderHook away for a single page.
- To render a Heroicon by a **dynamic string name** inside a plain Blade
  partial (not a Filament component's `->icon()`, which handles this itself)
  use the global `svg($name, $classOrAttributes)` helper from
  `blade-ui-kit/blade-icons` (the package backing both `heroicon-o-*` static
  tags and Filament's own `->icon()` resolution) — **never** `{!! svg(...) !!}`:
  it returns a `BladeUI\Icons\Svg` object implementing `Htmlable` (a `toHtml()`
  method, no `__toString()`), and Blade's raw `{!! !!}` echo does not know
  about `Htmlable` (it's a plain PHP `echo`, which throws "Object ... could
  not be converted to string"). Use `{{ svg(...) }}` instead — Laravel's `e()`
  helper (which `{{ }}` compiles to) explicitly checks `instanceof Htmlable`
  and calls `->toHtml()` without escaping, so the raw SVG markup still comes
  through unescaped despite the "safe" `{{ }}` syntax. Confirmed via a real
  500 error caught in `storage/logs/laravel.log` (not visible from the tinker
  `app()->handle($request)` response body itself, which just returns a
  generic error page — always tail the log file when a tinker-rendered page
  returns 500 with no useful HTML).
- For an Infolist entry that needs to render a whole custom Blade partial
  driven by data computed once per-request in PHP (not bound to any model
  attribute/state, e.g. a timeline/list built from a relationship) —
  `Filament\Infolists\Components\View::make($viewPath)->viewData($arrayOrClosure)`
  (the Infolist-native equivalent of `Forms\Components\*->view()`/`->viewData()`
  already used for form fields): plain array `viewData` works fine (no need
  for a closure) when the data is computed inline in the page's `infolist()`
  method, since that method itself already runs fresh per request. Alias the
  import (e.g. `use Filament\Infolists\Components\View as ViewInfolist;`) if
  the page already imports Laravel's own `Illuminate\Contracts\View\View` or
  similar under the plain `View` name.
