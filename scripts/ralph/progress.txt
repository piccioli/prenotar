## Codebase Patterns
- Filament `Pages\Auth\Login::authenticate()` checks `$user->canAccessPanel(Filament::getCurrentPanel())` for the CURRENT panel — a shared/neutral panel with no real resources needs its own Login subclass overriding `authenticate()` to check `canAccessPanel()` against the real panels instead (`admin`/`gr`/`sezione`), otherwise every login on that panel is rejected and immediately logged out.
- `Panel::getUrl()` builds its result via a `NavigationManager` that reads `Filament::getCurrentPanel()` internally (global state), NOT the panel instance it's called on — calling `Filament::getPanel('admin')->getUrl()` from a *different* panel's request context does not reliably resolve `/admin`. Use `url($panel->getPath())` instead when you need another panel's base URL from outside its own context.
- A panel can have `->path('')` (empty string) to serve routes at the domain root (e.g. a shared `/login` panel) without colliding with the other panels' non-empty path prefixes.
- Every new Filament `viteTheme()` entry point must be added to `input` in `vite.config.js` AND rebuilt with `sail npm run build` before the page is requested — otherwise Filament throws a Vite-manifest-not-found error. `public/build/manifest.json` is gitignored, so this rebuild has to happen in every environment (dev machine, CI, deploy) that serves the new panel, not just once.
- To test a Filament page/Livewire component tied to a panel, `Livewire::test(PageClass::class)` works stand-alone after `actingAs($user)` — no need for a preceding `get()` on the panel URL to resolve `Filament::getCurrentPanel()`. The stock Filament Login page's form state lives under `data.*` (`data.email`, `data.password`, `data.remember`), not direct component properties.
- `Panel::login()` accepts a `Closure` (not just `Login::class`/an array) — use this to neutralize a panel's stock login form (e.g. redirect it elsewhere) while keeping `hasLogin() === true`, which other Filament internals (`Authenticate` middleware's redirect-to-login-when-unauthenticated) depend on. Unlike `getUrl()`, `Panel::getLoginUrl()` is safe to call for a panel other than the current one — it resolves via a fully-qualified route name, not `Filament::getCurrentPanel()` global state.
- Filament panel routes are registered by the package's own `routes/web.php` (looping `Filament::getPanels()`), loaded before the app's `routes/web.php`. A `Route::redirect()`/`Route::get()` in the app's routes file for the same URI+method as a panel route is never reached — the first-registered route always wins on an exact match.

## 2026-07-13 - US-003
- Implementato il redirect (302) delle vecchie URL di login per-pannello (`/admin/login`, `/gr/login`, `/sezione/login`) verso il login unico `/login`.
- Approccio scelto DOPO aver verificato il rischio di rimuovere `->login()` dai 3 pannelli: `Filament\Http\Middleware\Authenticate::redirectTo()` chiama `Filament::getLoginUrl()`, che ritorna `null` se `$panel->hasLogin()` è `false` — un utente non autenticato che visita una pagina protetta di `/admin`, `/gr` o `/sezione` finirebbe nel fallback di Laravel `route('login')`, un nome di route inesistente in questa app (route exception / 500), altrimenti una regressione seria. Per questo `->login()` resta impostato su tutti e 3 i pannelli (così `hasLogin()` resta `true` e il redirect-a-login-quando-non-autenticato continua a funzionare), ma l'azione della route (di default `Filament\Pages\Auth\Login::class`) è sostituita da una closure che fa redirect verso il login unico.
- Files changed:
  - `app/Support/Auth/PanelRedirector.php`: aggiunto `loginUrl(): string` (usa `Filament::getPanel('login')->getLoginUrl()`, fallback `url('/login')`) — riusato dalle 3 closure di redirect invece di stringhe hardcoded duplicate.
  - `app/Providers/Filament/AdminPanelProvider.php`, `GrPanelProvider.php`, `SezionePanelProvider.php`: `->login()` → `->login(fn () => redirect(PanelRedirector::loginUrl()))`.
  - `tests/Feature/Auth/LoginBrandingTest.php`: i 3 test che asserivano `assertOk()` sulle vecchie URL (obsoleti con questa change, il branding neutro di `/login` è già coperto da `UnifiedLoginTest`) sono stati aggiornati per asserire `assertRedirect('/login')` — necessario per non lasciare `composer qa` rosso, anche se la revisione completa dell'architettura dei test di login è assegnata a US-004.
  - Nessuna modifica a `routes/web.php`: un `Route::redirect()` lì non avrebbe funzionato, perché le route dei pannelli Filament vengono registrate dal package provider (vedi `vendor/filament/filament/routes/web.php`) PRIMA che `routes/web.php` dell'app venga caricato — a parità di URI+metodo vince la prima route registrata, quindi qualsiasi redirect andava messo lato Filament (l'azione della route di login del pannello), non lato Laravel puro.
- Verificato anche manualmente con Sail in esecuzione: `curl -I http://localhost/admin/login` (e `/gr/login`, `/sezione/login`) → `302` con `Location: http://localhost/login`.
- **Learnings for future iterations:**
  - `Panel::login()` accetta anche una `Closure` oltre a `Login::class`/array — utile per "disattivare" una pagina di login stock senza perdere `hasLogin() === true` (necessario per non rompere il redirect automatico di `Filament\Http\Middleware\Authenticate` verso una pagina di login quando l'utente non è autenticato).
  - `Panel::getLoginUrl()` (a differenza di `Panel::getUrl()`, vedi bug NavigationManager in "Codebase Patterns") usa `route()` con nome di route completamente qualificato (`filament.<id>.auth.login`) e NON dipende da `Filament::getCurrentPanel()` — sicuro da chiamare per un pannello diverso da quello corrente.
  - Le route dei pannelli Filament sono registrate da `vendor/filament/filament/routes/web.php` (iterando `Filament::getPanels()`), caricato prima delle route applicative in `routes/web.php` — un `Route::redirect()`/`Route::get()` definito lì per lo stesso URI+metodo di una route di un pannello non viene mai raggiunto (vince sempre la prima route registrata a parità di match).
